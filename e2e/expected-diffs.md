# Expected differences: C against baseline B

Plan §8.5 and §10.8, step 19. Everything `/demo` shows on the v2 engine (C, the branch head) must match baseline B (tag `phase1-baseline-b`: v0 plus the route move, the Q14 tokens and the agent fix) pixel for pixel, except the differences listed here. Each one has a decided source, a region the pixel gate leaves out, and a text or state assertion of the v2 value in its place, at the frozen clock of 2026-10-14 10:00 Europe/Rome.

How the gate leaves a region out (`e2e/gate.ts`):

- **masked**: the region keeps its place and size in both builds. Both runs measure it, and the union of B's and C's boxes is painted over both images before the compare. So a label that is wider in one build can't leak a pixel.
- **collapsed**: the region's text is shorter or longer in v2, or its size follows the item ids, so everything after it moves. It is taken out of the layout (`display: none`) in both builds before the capture, and the page that remains (header, tabs, metrics, the rest of the view surface, the chrome) is compared whole at 0 pixels.
  - The region must be on the page in both builds before it is taken out, so a board that hasn't drawn yet can't pass unseen.
  - The record keeps both builds' page sizes with the region in place.
  - This is how decision 3 of the step ("clipped or per-element captures") is implemented.
  - Per-element crops of the shifted page were tried first and can't reach 0 pixels. A fractional vertical shift rasterises text and antialiased edges differently. The first gate run measured it: the Focus eyebrow crop was 13 px tall in B and 14 in C, and the title and next-step crops differed by 836 and 1,287 pixels with no change in their content.
- Frames (`motion.spec.ts`) are masked the same way, measured at each frame. A trigger whose expected region moves its neighbours (the Focus stack) masks the whole moving part.

The masks, collapsed regions and assertions live in `e2e/expected.ts` and in each state's `gate` in `e2e/states.ts`. The ED-9 assertions are in `e2e/interactions.spec.ts`. Assertions run on v2 builds only (`E2E_ENGINE`, which `compare.mjs` sets per commit).

## Harness changes for the gate (step 19)

- **Pointer and agent after ED-10.** Dismissing the first-load caption clicks next to the dock. The pointer then hovered the composer's chips and kept the agent awake, which B never sees. `App.firstLoadNotice` now parks the pointer at (0, 0) and waits for the agent to settle.
- **Clock alignment (frames).** A v2 build spends whole settle blocks on that caption, and the agent's breathing runs on the fake clock. With full motion, every stepped open now ends at `OPEN_MS` (24 s) after the frozen time, then settles. Both builds meet each trigger with the agent in the same, settled, phase.
- **Random streams (frames).** `Math.random` and `crypto` draw from two seeded streams, so v2's ids (crypto) never move the values the text scramble draws. `__e2e.reseed()` restarts both before each motion trigger, so whatever either build drew before the trigger (v0 mints ids with `Math.random`) can't shift a frame.
- **Images before a still.** The settle signal also waits for images. That means an `img` still loading, or the moodboard's pulsing placeholder while its blob is read from IndexedDB in real time.
- **Two-way rasterisations, held off at capture (2026-10-16).** The gate run on the final commit failed two stills that B and C both draw in two ways from one page load to the next. Neither is a change in the app: `src/` was byte-identical to `4210fd6`, whose run passed.
  - **Chromium, full-page screenshots.** `tracker-list` on `chromium-phone`, 6,382 px: the text of the view tabs, the metric eyebrows and the "Ask FORM" pill, 1 CSS px off.
    - To take a full-page screenshot, Chromium emulates a 1×1 view, then the capture size. Now and then the page is laid out at that tiny view in between. Under a Chromium flag that made it frequent, each of the 9 such captures logged a 1×1 resize and none of 39 others did; the path inside Chromium wasn't traced. The glass containers that Blink composites with their own paint offset then move by a fraction of a pixel and back, and Blink doesn't repaint their text after a subpixel move (crbug.com/833083).
    - Over 562 captures there were exactly two images, both drawn by both builds: B drew the second in 10 of 281, C in 20 of 281.
    - It wasn't only `tracker-list`. In a review's run of all states with `380da0b`'s gate, `tracker`'s first capture differed by the same 6,382 px, and B's references for `tracker`, `tracker-list`, `tracker-urgent` and `proposal` on `chromium-phone` differed from the baseline bytes. With the hold, all four match them.
    - In Chromium, `stableShot` now holds the document's width while it takes full-page screenshots (`hold` in `gate.ts`), so the page doesn't reflow at the tiny view. WebKit snapshots a full page in one pass without resizing the view, so it isn't held.
    - Only the width is held, and the app still gets the capture's `resize` events. A first version also added a capture-phase `resize` listener meant to stop them. It never did: in Chromium the window's listeners run in the order they were added, capture or not, so it ran after the app's, which subscribes at mount. A minimal page shows that order in Chromium (WebKit runs the capture listener first), and every measurement of that version is in effect the width alone. The listener is gone.
    - So during a held capture the "Ask FORM" pill (`useViewport`) still moves, to left −116 px and top −77 px at the 4×4 view the held width leaves, and back (it reached that view in 2 of 13 `tracker-list` tests probed). Those are whole pixels, so its text comes back as it was. A state whose pill landed on a fraction would draw a second image in both builds: a failure, not a pass.
    - Keeping the resize from the app was not pursued. It would take a listener registered before the app's, and it would hide a candidate whose resize handling changes the page, which the gate sees on `chromium-phone` because of these resizes (below: a candidate whose tablist gains a 1 px margin after any resize fails).
  - **WebKit, the ground's dot grid after a collapse.** `brief-client` on `webkit-phone`, 1,966 px: 1 to 5 grey levels on every dot of the first viewport.
    - WebKit draws `.ground`'s dots from an 11 px tile it caches for about 3 s (WebKit's main-branch source; Playwright's WebKit build may differ). A snapshot painted right after a layout change, before WebKit's next rendering update, can rasterise that tile itself, harder-edged, and the page keeps it. Which path rasterises it that way wasn't established.
    - Collapsing regions is such a layout change. Since `658bb10` measures them without a screenshot first, the first screenshot came right after the collapse.
    - Straight after the collapse, brief-client drew the second image in 12 of 72 captures of B and 28 of 72 of C. Given time to render, or a screenshot first, no capture drew it:
      - brief-client, both builds: a full-page screenshot before the collapse (`4210fd6`'s order), 0 of 48; one uncollapsed screenshot between the measurement and the collapse, 0 of 32; 1 s of real time after the collapse, 0 of 32.
      - brief-team, B only: 20, 60 or 200 ms after the collapse, 0 of 48 trials; 1 s, 0 of 8.
      - brief-client wasn't measured at 20 or 60 ms. At the gate's 200 ms it was, in both builds (below).
    - It wasn't only `brief-client` either. The final-commit run's B references for `brief-team` and `brief-short` on `webkit-phone` were the second image. A review's run with `380da0b`'s gate failed `focus`, `timeline` and `timeline-cleared-estimate` on `webkit-phone`, collapsed states an investigation had seen draw the same second image.
    - The gate now waits `COLLAPSE_RENDER_MS` (200 ms of real time) after the collapse, before the first screenshot.
    - Only there. A first version waited before every still's first screenshot. On a page at rest the second image then showed up more often: the webkit-desktop `composer` on C drew it in 5 of 42 captures with the wait, and in 0 of 40 without. That is an observation (Fisher two-sided p ≈ 0.055), not an established effect, but it gives no reason to wait there.
  - **Measured with the final gate** (width hold, 200 ms after a collapse, two captures per build). Setup: 2 workers, `--disable-gpu`, B writing one reference per repeat, then C compared with B's server up for the retries.
    - **The two failing stills.** `tracker-list` and `brief-client`, 30 comparisons each on both phone projects: C matched B at the first capture in 120 of 120, with no retry: 0 differing of 702.4 million compared pixels. B drew one image per still in all 30 of its captures: on `chromium-phone`, `tracker-list` in the baseline bytes (`e2e/baselines/B.json`); on `webkit-phone`, `brief-client` in the final-commit run's B reference bytes (the first dot image). So at the 200 ms wait both builds drew one image of `brief-client` in 60 of 60 captures.
    - **All 23 states on all four projects, once.** 92 of 92 matched at the first capture, with no retry: 0 differing of 287.9 million compared pixels. `compare.mjs`'s summary of those records: 23 of 23 per project, none passed only after a retry.
    - **B's bytes.** 63 of the 64 page stills B wrote are byte-identical to the 2026-10-14 baseline (`e2e/baselines/B.json`). The other is `palette` on `chromium-desktop`: its placeholder text alternates between two images 2 grey levels apart (1,083 px), which `THRESHOLD` absorbs, and `380da0b`'s gate drew both too (4 times each in 8 B captures). 26 of the 28 collapsed stills match the final-commit run's base. The other two are webkit-phone `brief-team` and `brief-short`, where that run's B had drawn the dot grid's second image and now draws the first.
    - **Before the fixes.** The same harness with `380da0b`'s gate: `tracker-list`'s first capture differed in 8 of 30, and B itself wrote the second image twice. `brief-client`'s first capture differed in 17 of 30, and 3 of 30 failed after the retries. A review interleaved the first version of these fixes with `380da0b`'s gate 25 times on both phone projects: 100 of 100 first-capture matches against 10 first-capture differences and 2 `brief-client` failures (first capture on `brief-client`: 0 of 25 against 9 of 25, Fisher p = 0.0016).
- **Retry protocol (stills).** The backstop for any other two-way rasterisation.
  - When a still differs, the state is reached again in a fresh context on C, then on B (`compare.mjs` keeps B's server up). That is two captures per build at most, the first ones included, as before 2026-10-16.
  - Each new capture is compared with every capture of the other build so far. The still passes only if some B capture and some C capture match exactly outside the expected differences: no pixel budget, and the threshold is unchanged.
  - Every capture and comparison is recorded, in order, in the gate's JSON and in the test's annotations. After retries, the JSON names the pair that matched (`matched`).
  - A pass after a retry isn't a clean pass. Its first capture differed: a quirk the gate doesn't hold off yet, or a change that shows on only some page loads. `compare.mjs` lists such stills apart, in its output and in `summary.json` (`passedAfterRetry` per project and spec, `gatePassedAfterRetry` in all).
  - A change in C's code is in every C capture, so it fails every pair. Measured on `tracker-list` and `brief-client` on both phone projects, with CSS added to C pages only, never to B's:
    - The view-tab labels moved 1 CSS px down inside the glass tablist. That is exactly the tabs band of Chromium's second image (7,168 px). It failed 8 of 8, each after all four pairs: 3,658 and 3,790 px on `chromium-phone` (`tracker-list`, `brief-client`), 3,743 and 3,670 px on `webkit-phone`.
    - The tablist's ink pill 3 grey levels lighter failed 4 of 4 the same way, at 9,808 to 14,927 px.
    - A tablist that gains a 1 px margin after any window resize failed 2 of 2 on `chromium-phone` `tracker-list`, after all four pairs: the capture is 3 device px taller (1170×5370 → 1170×5373), because Chromium's capture resizes the page.
    - A failing still takes 35 to 52 s (median 44 s) against 12 to 18 s for a passing one: two more reaches of its state, as before 2026-10-16.
    - A 1-level change passes, as it did before: `THRESHOLD` 0.01 lets two levels through (the first version measured 4 of 4).
  - **Why not more captures.** A change that shows on only some of C's page loads passes as soon as one C capture is clean. If it shows on a share q of loads, it passes with probability 1 − q² at two captures per build and 1 − q³ at three.
    - A first version took three per build. A review moved the tab labels 1 CSS px down on C's first two loads only: that version passed it 4 of 4, matching at C's third capture, while `380da0b`'s gate failed it 4 of 4.
    - With two captures per build the same change fails 8 of 8 (`tracker-list` and `brief-client` on both phone projects, twice each), after all four pairs.
    - A change on C's first load only passes, as it did with `380da0b`'s gate: 4 of 4, matching at C's second capture. `compare.mjs` lists all four as passed only after a retry.
    - With both quirks held off, no unmutated C still has needed a retry: none in this gate's 212 comparisons above, in the first version's 212 or in a review's 146. A third capture buys nothing.
  - **Why not retries alone.** At brief-client's measured rates (17% and 39%), two captures per build fail an estimated 11.5% of runs, and three per build would still fail about 3.5%. Retries don't absorb a quirk whose odds differ between the builds, so the fix is at capture.
- **Phone moodboard and full-page screenshots.** In full gate runs, the moodboard's board on `chromium-phone` sometimes measured a zero width right after a full-page screenshot. That screenshot fires a `resize` in phone emulation, and the board is drawn only once its width is known.
  - It happened in C in three runs and in B in one base run.
  - It never happened in five shorter runs, on the desktop or in WebKit.
  - The gate now measures the collapsed regions, and the page size they give, before any screenshot, and requires every one to be on the page.
  - `collageChecks` lets the board measure itself again before checking the tiles.
  - That `resize` is very likely Chromium's 1×1 view (above). Since 2026-10-16 the hold keeps the document's width during full-page screenshots, so the board shouldn't follow the tiny view, although the app still gets the `resize`. This was not reproduced on the moodboard itself, so the measurement order stays.
  - Phase 3 should check whether `useWidth`'s ResizeObserver can see a zero width during a mobile viewport resize in real use. The code is the same in v0 and v2.
- **A locked screen.** With the Mac's screen locked, Chromium's GPU compositing stalls every worker at once: tests hang in `clock.runFor` or in waits for real frames until their timeout. `E2E_CHROMIUM_ARGS=--disable-gpu` runs both builds of a comparison on software compositing, and the step 19 gate run used it. WebKit was unaffected in the same conditions. A wait for real frames now fails after 30 s with that hint, instead of hanging.
- **One fix in the app (not an expected difference).** The timeline's start pill drew "28 Sep 2026" as one text node, where v0 drew day, month and year as three. Chromium shapes each text node on its own, so the first glyph sat a fraction of a pixel off: 22 differing pixels in the desktop timeline still, and the same glyph in the frames that draw a timeline. `TimelineView` now renders v0's three text nodes. The fix restores B's bytes, checked by screenshot, and `TimelineView.test.tsx` pins the text nodes.
